# V2: Conversation-Aware Issues

Target: Mid/Late March 2026

---

## Release Announcement

**isq v2: Your issue tracker doesn't know what you're working on**

In agentic development, the unit of work isn't a commit. It's a conversation.

You open Claude Code, describe what you want, iterate through approaches, hit
dead ends, backtrack, and eventually land on something that works. Forty minutes
later you have a PR. The commit says "fix auth bug." The conversation that got
you there — the reasoning, the rejected approaches, the files you touched and
untouched — vanishes into `~/.claude/projects/`.

Your issue tracker sees "closed." Git sees a diff. Neither knows what actually
happened.

isq v2 fixes this.

**One command. Automatic linking.**

```
isq start ISQ-42
```

That's it. isq hooks into Claude Code and captures the conversation. When you're
done, `isq conversations ISQ-42` shows every session that touched that issue:
timestamps, duration, files modified, tools invoked. `--export` dumps the full
transcript for an agent to analyze.

No workflow change. No scanning. No polling. Claude Code's hook system tells isq
exactly when work starts and where the conversation lives.

**Cycle time that actually means something**

DORA says elite teams deploy in under a day. But DORA measures from first commit.
In agentic development, the first commit is the *end* of the work, not the
beginning.

isq measures from first prompt to merged PR:

```
$ isq metrics
Issue       Cycle Time    Sessions    Churn
ISQ-42      1h 11m        2           low
ISQ-38      6h 20m        4           high  ← retries in auth module
ISQ-41      22m           1           none
```

Median cycle time. Conversation count per issue. Churn signals that show where
your codebase fights back. This is the data DORA should have measured if AI
agents had existed in 2014.

**Data you own**

GitHub sees your commits. Linear sees your issues. Neither sees your agent
conversations — the actual record of how work gets done. That data lives on your
machine in JSONL files that most tools ignore.

isq indexes it locally. SQLite. Offline-first. No API calls, no telemetry, no
SaaS. The same architecture that makes `isq list` instant makes
`isq conversations` instant.

**Agents that learn**

The retrieval skill teaches Claude how to pull conversation history for any
issue. What happens next is up to the agent. Maybe it notices the auth module
caused 4 retry loops and opens an issue. Maybe it writes a design doc. Maybe it
updates a runbook. isq provides the data. The agent decides what's useful.

This is infrastructure for AI-native development: a local data layer connecting
issues to conversations, so agents can reason about how work actually happens.

**Try it**

```
curl -fsSL https://isq.sh/install | sh
isq link github
isq start 42
# work with Claude Code
isq metrics
```

v2 ships mid-March. GitHub, Linear, and JIRA. Claude Code first, other agents
to follow.

## Strategy

Use Claude Code hooks (not polling) for conversation-to-issue linking. The isq
plugin already ships hooks via `hooks/hooks.json`. A `PostToolUse` hook on Bash
detects `isq start <issue>` and captures `session_id` + `transcript_path` from
the hook input JSON. isq writes that mapping to SQLite. No scanning, no daemon
involvement for linking.

The `ConversationSource` trait handles **parsing** transcript files given a path,
not discovery. Claude Code JSONL is the first implementation. Same pattern as
Forge: trait normalizes to common types, enum dispatch, one impl per agent tool.

## Issues

### Plugin hook for conversation linking

Add a `PostToolUse` hook to the isq plugin's `hooks/hooks.json` that matches
Bash tool calls containing `isq start`. The hook receives `session_id` and
`transcript_path` on stdin. Call `isq` to record the mapping in SQLite.

### Schema migration for conversations

Add SQLite tables for conversations (id, transcript_path, start_time, end_time)
and conversation-to-issue mappings (conversation_id, issue_id). Same `PRAGMA
user_version` migration pattern as existing schema.

### ConversationSource trait

Define trait in `src/conversations/mod.rs` with common types (`Conversation`,
`ConversationDetail`). Conversation has: id, start/end timestamps, files touched,
tool invocations, token counts. The trait parses a transcript file given a path --
discovery/linking is handled by hooks, not by this trait.

### Claude Code ConversationSource implementation

First `ConversationSource` impl in `src/conversations/claude_code.rs`. Parse
`~/.claude/projects/` JSONL files into common types. The format is well-understood
(dozen+ community parsers exist).

### `isq conversations <issue>` command

List all conversations linked to an issue: timestamps, duration, files touched.
Supports `--json`. With `--export`, dump full conversation content in a portable
format for agent consumption.

### `isq metrics` command

Cycle time (first prompt to PR merged), conversation count per issue, churn
signals (files edited then reverted, retry loops). Supports `--json`.

### Conversation retrieval skill

Skill doc in `.claude-plugin/skills/` that teaches agents how to use
`isq conversations` to retrieve conversation history for issues. No opinion on
what the agent does with the data -- could write docs, file issues, refactor,
or do nothing.
